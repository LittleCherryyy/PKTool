# PKTool PCCS — experimental development

Independent PKTool fork, not part of Pokewalker Virtual or Virtual Slot-2.
Initial target: original English Pokemon Crystal to original English Pokemon Ruby, on Nintendo DSi with internal SD. Keep all original PKTool functionality.

## Status
Experimental read-only adapter. Not linked into the normal application; no save mutations, bank changes, transfer UI or working NDS conversion build yet. Existing generation restrictions remain unchanged. The adapter is isolated outside the normal build source glob until its external dependency and tests are ready.

## Conversion policy
Use PCCS LEGAL only. Reject eggs, held items, unsupported languages, invalid inputs and mythical/event remapping until tested. Reject uncertain source or destination legality findings except the narrowly scoped, documented PCCS SID=0 warning on fresh non-shiny FireRed-origin output. Retain the warning; no auto-legalizer fallback. Preserve species, shiny status, gender, form, nickname and original trainer identity where compatible. A raw PK2 alone cannot establish the source save edition. Game checks belong to the caller. No claim of official transfer or guaranteed Pokemon HOME compatibility.

## VPT002 host conversion probe
The independent VPT002 workflow fetches the exact PCCS pin into the ephemeral runner, builds its host library and PKTool's portable core, then executes three synthetic English Crystal starter fixtures through the actual LEGAL API and strict adapter. It checks encrypted PK3 serialization, decoded checksum and identity, independent legality checks, rejection of eggs, and source immutability. Any refusal of these fixtures is a test failure; preserve all independent legality findings. The job uploads no PCCS code or linked binaries. This is a test candidate until the job passes; no hardware or save transfer claims.

### First probe finding
[Run 45594895514](https://github.com/LittleCherryyy/PKTool/actions/runs/45594895514) built both libraries and linked the adapter; all three converted fixtures failed the PK3 checksum/identity gate. PCCS infers encryption from checksum mismatch. Fresh conversion output requires explicit checksum initialization, as in the upstream convertPKs example. The follow-up initializes this checksum before asking for canonical plaintext and checks both upstream serialization paths against PKTool. Results still require CI verification.

### SID warning policy
[Run 45595073605](https://github.com/LittleCherryyy/PKTool/actions/runs/45595073605) confirmed successful checksum/identity and canonical/encrypted serialization checks for all three starter fixtures. Each was rejected by strict preview solely because the native checker emitted "SID is 0" (Warning, not Invalid). The pinned PCCS source GBPokemon::convertShininess explicitly sets SID=0 for non-shiny Pokemon unless that would cause unintended shininess. The original source has no SID. The bridge therefore recognizes only that warning on fresh non-shiny FireRed-origin PCCS LEGAL output with nonzero TID, no egg or mythical, and independently checks the shiny calculation. It never changes the SID, suppresses the displayed warning, accepts any Invalid finding, or accepts other warnings. The standard PKTool checker remains unchanged. This is not proof of official provenance or Pokemon HOME acceptance.

## VPT004 staged save images
Host-only integration candidate. ## VPT005 POSIX recovery prototype
A host-only single-writer prototype persists an immutable, versioned and CRC32-checked journal containing both original and staged save images and normalized paths. It uses exclusive creation, exact readback and file/directory fsync, then destination-first replacement using separate original sidecars. Recovery classifies exact before/moved/after states and refuses unexpected content, wrong paths and corrupt journal data. Retain the journal and both original sidecars; no automatic cleanup or retry on conflict. Synthetic tests exercise normal completion, interruption after each original rename and after destination persistence, idempotent resume and conflict rejection. CRC32 detects accidental corruption, not malicious modification. No concurrent writers supported. This POSIX prototype is not a FAT/libfat implementation, and power-loss durability on physical SD remains unverified. A FAT-compatible storage backend, pending-transfer startup gate and archive workflow are required before user-facing use. No PCCS-linked binaries distributed.

## VPT006A internal SD storage backend
VPT005 passed [host persistence tests](https://github.com/LittleCherryyy/PKTool/actions/runs/45609133711). The ARM9 candidate now compiles the same journal state machine with a libfat-compatible backend: explicit sd:/ paths, ASCII component restrictions and case-folded collision checks, exclusive creation, exact streamed readback, file fsync and non-overwriting rename. Upstream libfat fatfile.c supports O_EXCL and flushes modified files on fsync/close; fatdir.c flushes its cache after successful rename. Directory fsync is not supported and is not claimed. The host test exercises the FAT path policy and state machine on POSIX, not an emulated or physical FAT filesystem. The ARM9 build-only diagnostic references the journal functions without calling them; no SD writes or linked binary publication. Runtime heap/stack, FAT failure and power-loss behavior, pending-transfer startup gate, provenance and archive workflow remain unvalidated. Do not enable real save migration yet. The pinned PCCS license remains unresolved.

## VPT006D startup gate
VPT006C [host tests](https://github.com/LittleCherryyy/PKTool/actions/runs/45624605943) and [ARM9 link](https://github.com/LittleCherryyy/PKTool/actions/runs/45624605805) passed. The optional DSi preview checks sd:/PKTOOL/transporter/active.vpt and its .new sidecar at startup. Missing journal on a fresh installation is clear; partial creation, corruption, unexpected files or inconsistent transaction state block the editor. Pending and completed transactions also block until recovery or archiving. The recovery screen offers read-only recheck and exit. An explicit host-tested recovery API reads the stored paths and resumes exact recorded images; the UI does not call it yet. Tests cover missing directory, incomplete/corrupt journal, pending, conflict, resume and complete. Archiving, user-initiated commit, runtime memory and physical SD testing remain gates; no PCCS-linked binaries are distributed. The gate applies only to this optional build, not external emulators or other PKTool versions.

## VPT007 candidate: experimental write flow
VPT006D [ARM9](https://github.com/LittleCherryyy/PKTool/actions/runs/45624945547) and [host](https://github.com/LittleCherryyy/PKTool/actions/runs/45624945522) passed. VPT007 adds explicit START twice on a successful preview, exact journal persistence, destination-first recovery, and an explicit X archive action. A completed transaction remains locked until its full journal is copied to a separate archive and verified; original sidecars are then removed, the active journal is removed last. A restart after sidecar cleanup recognizes the completed state only if the archive matches every journal byte. Corrupt/partial archive or conflicting files stop without automatic deletion. No automatic recovery on boot. The separate VPT_TRANSPORTER_WRITE flag is enabled only by the disposable ARM9 CI candidate; regular PKTool builds stay unchanged. This candidate is not validated on hardware and no linked binary is uploaded. English Crystal to English Ruby/Sapphire boxes only; user must verify actual game editions, not just save detection. No official transfer or guarantee of legality/HOME acceptance. PCCS redistribution permission is still unresolved.

### End-to-end UI gate and local test procedure
The host workflow builds the actual optional UI and drives its key input through selection, cancellation, double START commit, application restart, editor lock, archive, and verification of both saved Pokemon boxes. No user saves are used. The ARM9 candidate sets explicit internal SD paths in DSi mode. The build script discards linked files in CI. With permission to use the pinned PCCS dependency, a private local build can be retained by running `VPT_KEEP_LOCAL=1 bash experiments/pccs/build_arm9_probe.sh` in a disposable Linux/devkitARM checkout of this branch (the script modifies that checkout and downloads the pinned source). Do not redistribute the linked result without permission. For hardware tests use disposable English Crystal and Ruby/Sapphire saves on internal SD, not the originals: run in DSi mode, complete the read-only startup conversion probe, press Y on Home, select source/boxed Pokemon/destination/empty slot, review legality notes, START twice, then X to archive when complete. Open the games only after archive succeeds. If the recovery screen is blocked, retain all files and stop. Physical SD durability, runtime heap and emulator compatibility still require hardware validation.

## VPT008: first DSi feedback
VPT007 reached the conversion review on physical DSi but reported the generic path/transaction conflict. The visible Crystal path contains a precomposed e-acute, rejected by the ASCII-only FAT policy. VPT008 permits well-formed UTF-8 Latin-1 letters and folds their upper/lowercase variants for collision checks. It preserves exact spelling and other path and sidecar protections, avoids redundant trailing slashes in parent stat calls, and displays detailed refusal reasons. Host tests exercise accented filenames and directories, case aliases, malformed encoding, recovery and archival. Actual FAT and conversion on hardware remain unverified. No rename is required for supported names.

## VPT009 Crystal hatch encounter verification
Hardware feedback: VPT008 reached source legality checks. The selected entity was reported as a Day-Care egg encounter with a caught-data mismatch. The core checker previously required the suggested Goldenrod hatch location for all hatched Crystal Pokemon. Crystal records the actual location and uses caught level 1 as the hatch marker; PKHeX EncounterVerifier.VerifyEncounterEgg2 accepts location IDs up to 95. The checker now accepts hatch locations 1..95 with marker 1 (unhatched eggs require location 0); no general legality bypass is added. Source refusals show species, met level/location/time and prioritized non-valid findings. Synthetic regression tests cover valid and invalid hatch markers/locations. The precise user entity has not been inspected, so this is a targeted candidate fix, not confirmed hardware resolution.
